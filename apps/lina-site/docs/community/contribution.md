最有价值的贡献通常足够聚焦、可以复现，并且符合框架边界。

## 贡献方式

| 贡献类型 | 建议标准 |
| --- | --- |
| 缺陷反馈 | 包含版本、命令、预期行为、实际行为，以及去除敏感信息后的日志。 |
| 文档修正 | 如果页面是双语内容，需要同步更新中文和英文。 |
| 功能提案 | 当行为、架构或测试需要演进时，优先从`OpenSpec`变更开始。 |
| 代码变更 | 保持变更范围聚焦，补充针对性测试，避免无关重构。 |
| 插件示例 | 遵循`plugin-demo-source`或`plugin-demo-dynamic`的目录结构。 |

## 文档流程

官网内容遵循中文先行流程。先确认中文内容，再同步英文版本；英文需要使用自然表达，不做逐字翻译。

编辑官网文档时，请遵守以下约定：

1. 保持`frontmatter`完整，包括`description`和`keywords`。
2. 架构图和流程图优先使用`Mermaid`。
3. 配置项、模块清单和命令说明优先使用简洁表格。
4. 示例内容需要以`linapro`源码仓库中的事实为依据。

## 代码流程

提交代码时，建议使用聚焦的`Pull Request`说明问题、方案和验证方式。涉及共享行为、插件生命周期或用户可见流程的变更，应补充能够捕捉回归的测试。
