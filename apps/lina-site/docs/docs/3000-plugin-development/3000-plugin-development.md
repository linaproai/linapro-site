## 为什么需要两种插件模式

`LinaPro`的插件系统支持两种截然不同的交付模式，是因为现实中存在两类本质上不同的扩展需求：

### 需求一：长期稳定的业务功能

组织架构管理、文章内容管理、订单处理——这类功能需要长期迭代和维护，与系统核心紧密协作，对性能有一定要求。源码插件与宿主一起编译，直接调用宿主提供的`Go`包，性能最优、工具链最简单。

### 需求二：动态、临时或商业化的扩展

- 让`AI`在生产环境中临时开发并注入一个新功能，验证后决定是否保留
- 发现线上`Bug`，需要在不停机的情况下快速注入修复逻辑
- 作为商业`ISV`，以二进制形式分发插件能力，不暴露源代码
- 让第三方开发者开发插件并分发给用户，用户自行上传安装

这类需求是源码插件无法满足的——源码插件需要重新编译整个宿主才能生效，而`WASM`动态插件可以在运行时直接上传并立即生效。

## 两种模式详细对比

| 维度 | 源码插件 | `WASM`动态插件 |
|------|---------|--------------|
| **热加载** | ❌ 需要重启宿主 | ✅ 运行时即插即用，无需重启 |
| **性能** | ✅ 原生`Go`性能 | ⚠️ 有沙箱调用开销，约低 10-30% |
| **开发复杂度** | ✅ 低，标准`Go`开发 | ⚠️ 需了解`WASM`构建和受限接口 |
| **宿主服务访问** | ✅ 直接调用宿主包 | ⚠️ 通过桥接接口访问，有限制 |
| **调试体验** | ✅ 标准`Go`调试工具 | ⚠️ 调试相对复杂 |
| **源码保护** | ❌ 源码与宿主一起管理 | ✅ 只分发`.wasm`二进制 |
| **独立升级** | ❌ 需重新部署宿主 | ✅ 独立上传新版本`.wasm` |
| **跨平台性** | ❌ 需重新编译 | ✅ 编译一次，任意平台运行 |
| **隔离程度** | 命名空间隔离 | 完整`WASM`沙箱隔离 |
| **适用场景** | 长期业务功能 | 临时功能、热修复、商业分发 |

## 选型建议

**优先选择源码插件：** 大多数业务功能开发推荐使用源码插件，开发体验好、性能优、调试方便，与`LinaPro`的`AI`原生研发工作流和内置`AI`技能体系（`goframe-v2`、`lina-e2e`、`lina-review`等）完美契合，`AI`在开发插件的每个环节都能做出符合框架规范的专业决策。

**选择动态插件的场景：**


以下任一条件满足，考虑动态插件：

- 需要热加载，不能重启宿主
- 生产环境紧急修复（最小化停机风险）
- 不希望分发源代码（商业插件）
- 允许最终用户自行上传和管理插件
- 让 AI 快速开发验证性功能，随时可以卸载


## 动态插件的核心价值

动态插件的热加载能力在以下场景中特别有价值：

### 临时开发动态注入

你可以让`Claude Code`（或其他`AI`工具）开发一个`WASM`插件，构建后直接上传到运行中的系统，无需停机。验证效果满意后再决定是否转为源码插件长期维护。

```
# 示例：让 AI 快速开发一个临时的数据统计面板
让 Claude Code：开发一个显示今日新增用户数量的统计面板动态插件
```

### 生产环境热修复

当生产系统出现紧急问题，通过动态插件注入修复逻辑，可以将停机时间从「部署整个宿主」（可能几分钟）缩短到「上传一个`.wasm`文件」（几秒钟）。

### 商业插件分发

插件开发商可以将插件编译为`.wasm`二进制文件分发，用户直接上传安装，无需接触源代码，也无需重新编译宿主服务。
