## Overview

Source plugins are the most common extension mechanism in `LinaPro`. Compiled and deployed together with the host, they interact with the host through the stable interfaces provided by the `pluginhost` package. Plugins remain isolated from each other while sharing the host's governance capabilities — authentication, authorization, logging, scheduling, and more.

## Directory Structure

Every source plugin follows a uniform directory structure:

```text
apps/lina-plugins/<plugin-id>/
├── plugin.yaml                     # Plugin manifest (metadata and menu declarations)
├── plugin_embed.go                 # Embedded resource registration entry
├── backend/
│   ├── api/                        # Plugin API DTOs and route contracts
│   ├── internal/
│   │   ├── controller/             # HTTP controllers
│   │   ├── service/                # Business logic (the only permitted location)
│   │   ├── dao/                    # Data access layer (generated by gf gen dao)
│   │   └── model/
│   │       ├── do/                 # Data operation objects (generated by gf gen dao)
│   │       └── entity/             # Database entities (generated by gf gen dao)
│   ├── hack/config.yaml            # Plugin code generation configuration
│   └── plugin.go                   # Plugin backend registration entry
├── frontend/
│   └── pages/                      # Plugin frontend pages (Vue single-file components)
├── manifest/
│   ├── sql/                        # Install SQL (CREATE TABLE, etc.)
│   │   ├── mock-data/              # Demo data (optional)
│   │   └── uninstall/              # Uninstall SQL (DROP TABLE, etc.)
│   └── i18n/                       # Plugin runtime language packs (optional)
│       └── <locale>/apidoc/        # Plugin API documentation language packs (optional)
├── README.md
└── README.zh_CN.md
```

:::tip
`backend/internal/service/` is the only permitted location for plugin service components. Do not create a `service/` directory at the `backend/` root.
:::

## Building Your First Source Plugin

The following walkthrough creates a `content-article` (article management) plugin as a complete example.

:::info
The steps below are what an AI coding tool performs automatically. Developers can use this as a reference.
:::

### Step 1: Create the directory

```bash
mkdir -p apps/lina-plugins/content-article/{backend/api,backend/internal/{controller,service,dao,model/{do,entity}},frontend/pages,manifest/{sql,sql/mock-data,sql/uninstall,i18n}}
```

### Step 2: Write the plugin manifest

`plugin.yaml` declares the plugin's metadata and menus:

```yaml
# Unique plugin identifier (kebab-case), globally unique, used as database table prefix and file namespace
id: content-article
# Display name
name: Article Management
# Semantic version (semver format), compared by the host at upgrade time
version: v0.1.0
# Plugin type: source means compiled and deployed with the host
type: source
# Short description
description: Provides CRUD management for article content
# Author
author: linapro
# License
license: Apache-2.0

# Menu declarations — automatically registered by the host when the plugin is enabled
menus:
  - key: plugin:content-article:list       # Menu key, format: plugin:<plugin-id>:<feature>
    name: Article Management               # Display name (supports i18n keys)
    path: content-article-list             # Frontend route path, globally unique
    component: system/plugin/dynamic-page  # Plugin pages always use this component
    perms: content-article:article:view    # Required permission identifier
    icon: ant-design:file-text-outlined    # Menu icon (Ant Design icon name)
    type: M                                # Menu type: M=menu, C=directory, B=button
    sort: 1                                # Sort order; lower numbers appear first
    remark: Article management menu        # Optional remark
  - key: plugin:content-article:create
    parent_key: plugin:content-article:list  # Parent key — mounted under the list menu
    name: Create Article
    perms: content-article:article:create
    type: B                                  # B=button permission, not shown in the sidebar
    sort: 1
  - key: plugin:content-article:update
    parent_key: plugin:content-article:list
    name: Edit Article
    perms: content-article:article:update
    type: B
    sort: 2
  - key: plugin:content-article:delete
    parent_key: plugin:content-article:list
    name: Delete Article
    perms: content-article:article:delete
    type: B
    sort: 3
```

### Step 3: Write the install SQL

Install SQL must be idempotent (`IF NOT EXISTS`) so that repeated execution does not fail:

```sql
-- manifest/sql/001-init.sql
CREATE TABLE IF NOT EXISTS `content_article_record` (
    `id`         BIGINT       NOT NULL AUTO_INCREMENT COMMENT 'Article ID',
    `title`      VARCHAR(255) NOT NULL               COMMENT 'Article title',
    `content`    LONGTEXT     NOT NULL               COMMENT 'Article content',
    `status`     TINYINT      NOT NULL DEFAULT 0     COMMENT 'Status: 0=draft 1=published',
    `created_by` BIGINT       NOT NULL DEFAULT 0     COMMENT 'Creator ID',
    `created_at` DATETIME     NOT NULL               COMMENT 'Created at',
    `updated_at` DATETIME     NOT NULL               COMMENT 'Updated at',
    PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='Article record table';
```

Uninstall SQL:

```sql
-- manifest/sql/uninstall/001-cleanup.sql
DROP TABLE IF EXISTS `content_article_record`;
```

### Step 4: Define the API interface

```go
// backend/api/article/article.go
package article

import "github.com/gogf/gf/v2/frame/g"

type ArticleListReq struct {
    g.Meta   `path:"/plugin/content-article/article" method:"get" tags:"Article Management" summary:"Article list" middleware:"AuthMiddleware,PermMiddleware" perm:"content-article:article:view"`
    Page     int    `json:"page"     v:"min:1"          dc:"Page number"`
    PageSize int    `json:"pageSize" v:"min:1,max:100"  dc:"Page size"`
}

type ArticleCreateReq struct {
    g.Meta  `path:"/plugin/content-article/article" method:"post" tags:"Article Management" summary:"Create article" middleware:"AuthMiddleware,PermMiddleware" perm:"content-article:article:create"`
    Title   string `json:"title"   v:"required|length:1,255" dc:"Article title"`
    Content string `json:"content" v:"required"              dc:"Article content"`
}
```

### Step 5: Implement the service layer

```go
// backend/internal/service/article.go
package service

import (
    "context"
    "github.com/linaproai/linapro/apps/lina-plugins/content-article/backend/internal/dao"
)

type ArticleService struct{}

func (s *ArticleService) List(ctx context.Context, page, pageSize int) (list interface{}, total int, err error) {
    // Use the plugin's own DAO layer to access the database
    // The database table was created by the install SQL
    return dao.ContentArticleRecord.Ctx(ctx).Page(page, pageSize).All()
}
```

### Step 6: Register the plugin

```go
// backend/plugin.go
package backend

import (
    "github.com/linaproai/linapro/apps/lina-core/pkg/pluginhost"
    "github.com/linaproai/linapro/apps/lina-plugins/content-article/backend/internal/controller"
)

func Register(p pluginhost.SourcePlugin) {
    // Bind frontend assets (imported from plugin_embed.go)
    p.Assets().UseEmbeddedFiles(embedFS)

    // Register plugin HTTP routes
    p.HTTP().RegisterRoutes(
        pluginhost.ExtensionPointHTTPRouteRegister,
        pluginhost.CallbackExecutionModeBlocking,
        func(group *ghttp.RouterGroup) {
            group.Bind(controller.NewArticleController())
        },
    )

    // Register uninstall cleanup logic (runs before SQL drops the tables)
    p.Lifecycle().RegisterUninstallHandler(func(ctx context.Context, keepData bool) error {
        if !keepData {
            // Clean up plugin-uploaded files
        }
        return nil
    })
}
```

Wire it up in the host's plugin registration file:

```go
// apps/lina-plugins/lina-plugins.go
import contentarticle "github.com/linaproai/linapro/apps/lina-plugins/content-article/backend"

func init() {
    pluginregistry.Register("content-article", contentarticle.Register)
}
```

## Database Access

Plugins use `GoFrame`'s `gf gen dao` command to generate the data access layer. The plugin's DAO layer is completely independent from the host's DAO layer, with database namespace isolation:

```bash
# Run from the plugin's backend/ directory
cd apps/lina-plugins/content-article/backend
gf gen dao
```

The `hack/config.yaml` configuration file points to the plugin's own tables:

```yaml
gfcli:
  gen:
    dao:
      - link: "pgsql:postgres:postgres@tcp(127.0.0.1:5432)/linapro?sslmode=disable"
        tables: "content_article_*"  # Only generate DAO for the plugin's own tables
        descriptionTag: true
```

## Frontend Pages

Plugin frontend pages live under `frontend/pages/`. The framework automatically discovers and mounts them into the host workspace's dynamic routing:

```vue
<!-- frontend/pages/article-list.vue -->
<template>
  <div class="article-list">
    <!-- Use VXE Table to display the article list -->
    <vxe-grid v-bind="gridOptions" />
  </div>
</template>

<script setup lang="ts">
import { onMounted, ref } from 'vue'
import { useRequest } from '@vben/hooks'

const { loading, data, run } = useRequest(() =>
  fetch('/api/v1/plugin/content-article/article')
)

onMounted(() => run())
</script>
```

## Event Hooks

Plugins can listen to lifecycle events published by the host and execute their own logic at the right moment:

```go
// Listen for the login success event to record login logs
p.Hooks().RegisterHook(
    pluginhost.ExtensionPointAuthLoginSucceeded,
    pluginhost.CallbackExecutionModeAsync,  // Async — does not block the login flow
    func(ctx context.Context, payload *pluginhost.HookPayload) error {
        // Write login information to the plugin's own log table
        return recordLoginLog(ctx, payload)
    },
)
```

## Plugin Version Upgrades

When a plugin releases a new version (by updating the `version` field in `plugin.yaml`), the upgrade process is:

1. At startup, the host scans and detects the new version (`plugin.yaml` version > version recorded in the database)
2. If a version mismatch is found, **the host fails to start** and prompts you to run the upgrade command
3. Run the upgrade through the `lina-upgrade` AI skill:

```
# In Claude Code
upgrade source plugin content-article
```

4. Restart the host after the upgrade completes; the new version takes effect

## Best Practices

- Plugin `ID` uses `kebab-case`; the database table prefix uses the corresponding `snake_case` (e.g., `content-article` → `content_article_`)
- Install SQL uses `IF NOT EXISTS` to ensure idempotency
- All plugin service logic lives under `backend/internal/service/`; do not create `service/` elsewhere
- Menu `key` must follow the `plugin:<plugin-id>:<menu-key>` format
- Uninstall SQL covers complete cleanup logic; handle non-database resources (files, etc.) in `RegisterUninstallHandler`
- Use `apps/lina-plugins/plugin-demo-source` as a development template
