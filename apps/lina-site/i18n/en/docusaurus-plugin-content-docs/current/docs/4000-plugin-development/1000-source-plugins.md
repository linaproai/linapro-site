## Overview

Source plugins are the most common extension form in `LinaPro`. They are compiled and deployed together with the host, collaborating through the stable interfaces provided by the `pluginhost` package. Plugins remain isolated from each other while sharing the host's governance capabilities — authentication, permissions, logging, scheduling, multi-tenant context, and more.

Official source plugins live in `apps/lina-plugins/`, which is mounted as a `Git` submodule in the main framework repository. You can skip initializing the submodule when running only the host core; before developing, building, or testing official plugins, run `git submodule update --init --recursive` to pull the plugin workspace.

## Directory Structure

Every source plugin follows a uniform directory layout:

```text
apps/lina-plugins/<plugin-id>/
├── plugin.yaml                     # Plugin manifest (metadata, menu declarations)
├── plugin_embed.go                 # Embedded resource registration entry
├── backend/
│   ├── api/                        # Plugin API DTOs and route contracts
│   ├── internal/
│   │   ├── controller/             # HTTP controllers
│   │   ├── service/                # Business logic layer (the only allowed service location)
│   │   ├── dao/                    # Data access layer (generated by gf gen dao)
│   │   └── model/
│   │       ├── do/                 # Data operation objects (generated by gf gen dao)
│   │       └── entity/             # Database entities (generated by gf gen dao)
│   ├── hack/config.yaml            # Plugin code generation config
│   └── plugin.go                   # Plugin backend registration entry
├── frontend/
│   └── pages/                      # Plugin frontend pages (Vue SFCs)
├── manifest/
│   ├── sql/                        # Installation SQL (CREATE TABLE, etc.)
│   │   ├── mock-data/              # Demo data (optional)
│   │   └── uninstall/              # Uninstallation SQL (DROP TABLE, etc.)
│   └── i18n/                       # Plugin runtime language packs (optional)
│       └── <locale>/apidoc/        # Plugin API doc language packs (optional)
├── README.md
└── README.zh-CN.md
```

:::tip
`backend/internal/service/` is the only allowed location for plugin service components. Do not create a `service/` directory under `backend/` directly.
:::

## Creating Your First Source Plugin

Below is the complete development workflow for a `content-article` (article management) plugin:

:::info Note
These are the steps that an `AI Coding` tool would follow to develop a plugin automatically. Developers can use them as a learning reference.
:::

### Step 1: Create the Directory

```bash
mkdir -p apps/lina-plugins/content-article/{backend/api,backend/internal/{controller,service,dao,model/{do,entity}},frontend/pages,manifest/{sql,sql/mock-data,sql/uninstall,i18n}}
```

### Step 2: Write the Plugin Manifest

`plugin.yaml` declares the plugin's metadata and menus:

```yaml
# Unique plugin identifier (kebab-case), globally unique, used as DB table prefix and file namespace
id: content-article
# Plugin display name
name: Article Management
# Semantic version (semver); the host compares this on upgrade
version: v0.1.0
# Plugin type: source means it is compiled with the host
type: source
# Multi-tenant scope: platform_only = platform-context only; tenant_aware = can enter tenant context
scope_nature: tenant_aware
# Whether it supports tenant-scoped installation, provisioning, and data isolation
supports_multi_tenant: true
# Default install mode: global = enabled globally; tenant_scoped = independently enabled per tenant
default_install_mode: tenant_scoped
# Brief description
description: Provides CRUD management for article content
# Author
author: linapro
# License
license: Apache-2.0

# Menu declarations — the host registers them automatically when the plugin is enabled
menus:
  - key: plugin:content-article:list   # Unique menu key, format: plugin:<plugin-id>:<feature>
    name: Article Management            # Display name (supports i18n keys)
    path: content-article-list          # Frontend route path, globally unique
    component: system/plugin/dynamic-page  # Fixed component for plugin pages, dynamically loaded by host
    perms: content-article:article:view # Permission required to access this menu
    icon: ant-design:file-text-outlined # Menu icon (Iconify icon name)
    type: M                             # Menu type: D=directory, M=menu item, B=button
    sort: 1                             # Sort weight, lower values appear first
    remark: Article management menu     # Optional remark
  - key: plugin:content-article:create
    parent_key: plugin:content-article:list  # Parent menu key, nested under the list menu
    name: Create Article
    perms: content-article:article:create    # Button-level permission
    type: B                                  # B=button permission, not shown in sidebar
    sort: 1
  - key: plugin:content-article:update
    parent_key: plugin:content-article:list
    name: Edit Article
    perms: content-article:article:update
    type: B
    sort: 2
  - key: plugin:content-article:delete
    parent_key: plugin:content-article:list
    name: Delete Article
    perms: content-article:article:delete
    type: B
    sort: 3
```

### Step 3: Write the Installation SQL

Installation `SQL` must be idempotent (using `IF NOT EXISTS` for tables and indexes, and repeatable data-insertion statements) so that re-execution never fails. The current default database is `PostgreSQL 14+`; plugin installation scripts should use `PostgreSQL` dialect:

```sql
-- manifest/sql/001-init.sql
CREATE TABLE IF NOT EXISTS content_article_record (
    "id"         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    "tenant_id"  INT          NOT NULL DEFAULT 0,
    "title"      VARCHAR(255) NOT NULL DEFAULT '',
    "content"    TEXT         NOT NULL DEFAULT '',
    "status"     SMALLINT     NOT NULL DEFAULT 0,
    "created_by" BIGINT       NOT NULL DEFAULT 0,
    "created_at" TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    "updated_at" TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP
);

COMMENT ON TABLE content_article_record IS 'Article record table';
COMMENT ON COLUMN content_article_record."tenant_id" IS 'Owning tenant ID, 0 means PLATFORM';

CREATE INDEX IF NOT EXISTS idx_content_article_record_tenant_status
    ON content_article_record ("tenant_id", "status");
```

Uninstallation SQL:

```sql
-- manifest/sql/uninstall/001-cleanup.sql
DROP TABLE IF EXISTS content_article_record;
```

### Step 4: Define API Interfaces

```go
// backend/api/article/v1/article_list.go
package v1

import "github.com/gogf/gf/v2/frame/g"

type ArticleListReq struct {
    g.Meta   `path:"/plugins/content-article/article" method:"get" tags:"Article Management" summary:"Article list" permission:"content-article:article:view"`
    Page     int    `json:"page"     v:"min:1"          dc:"Page number"`
    PageSize int    `json:"pageSize" v:"min:1,max:100"  dc:"Page size"`
}

// backend/api/article/v1/article_create.go
type ArticleCreateReq struct {
    g.Meta  `path:"/plugins/content-article/article" method:"post" tags:"Article Management" summary:"Create article" permission:"content-article:article:create"`
    Title   string `json:"title"   v:"required|length:1,255" dc:"Article title"`
    Content string `json:"content" v:"required"              dc:"Article content"`
}
```

### Step 5: Implement the Service Layer

```go
// backend/internal/service/article.go
package service

import (
    "context"
    "github.com/linaproai/linapro/apps/lina-plugins/content-article/backend/internal/dao"
)

type ArticleService struct{}

func (s *ArticleService) List(ctx context.Context, page, pageSize int) (list interface{}, total int, err error) {
    // Use the plugin's own DAO layer to access the database
    // The table was created in the installation SQL
    return dao.ContentArticleRecord.Ctx(ctx).Page(page, pageSize).All()
}
```

### Step 6: Register the Plugin

Each plugin's `backend/` entry file performs self-registration in `init()`, with no external explicit call needed:

```go
// backend/plugin.go
package backend

import (
    "context"

    contentarticle "lina-plugin-content-article"
    "lina-core/pkg/pluginhost"
    articlectrl "lina-plugin-content-article/backend/internal/controller/article"
    articlesvc "lina-plugin-content-article/backend/internal/service/article"
)

const pluginID = "content-article"

func init() {
    plugin := pluginhost.NewSourcePlugin(pluginID)

    // Bind plugin embedded resources (plugin.yaml, manifest/, frontend/)
    plugin.Assets().UseEmbeddedFiles(contentarticle.EmbeddedFiles)

    // Register plugin HTTP routes
    plugin.HTTP().RegisterRoutes(
        pluginhost.ExtensionPointHTTPRouteRegister,
        pluginhost.CallbackExecutionModeBlocking,
        registerRoutes,
    )

    // Register uninstall cleanup logic (clean files before SQL drops tables)
    plugin.Lifecycle().RegisterUninstallHandler(func(ctx context.Context, input pluginhost.SourcePluginUninstallInput) error {
        if !input.PurgeStorageData() {
            return nil
        }
        // Clean up plugin-uploaded files
        return articlesvc.PurgeStorageData(ctx)
    })

    pluginhost.RegisterSourcePlugin(plugin)
}

// registerRoutes uses the host's published middleware catalog to register plugin routes.
func registerRoutes(ctx context.Context, registrar pluginhost.HTTPRegistrar) error {
    svc := articlesvc.New(registrar.HostServices().I18n(), registrar.HostServices().TenantFilter())
    ctrl := articlectrl.NewV1(svc)
    routes := registrar.Routes()
    middlewares := routes.Middlewares()
    routes.Group("/api/v1", func(group pluginhost.RouteGroup) {
        group.Middleware(
            middlewares.NeverDoneCtx(),
            middlewares.HandlerResponse(),
            middlewares.CORS(),
            middlewares.Ctx(),
        )
        group.Group("/", func(group pluginhost.RouteGroup) {
            group.Middleware(
                middlewares.Auth(),
                middlewares.Tenancy(),
                middlewares.Permission(),
            )
            group.Bind(
                ctrl.ListArticles,
                ctrl.CreateArticle,
            )
        })
    })
    return nil
}
```

Plugins self-register by calling `pluginhost.RegisterSourcePlugin(plugin)` in their `init()`. During a `plugin-full` build, `linactl` auto-generates an aggregation entry file `plugins.go` containing blank imports for all configured plugins:

```go
// apps/lina-plugins/plugins.go (auto-generated by linactl — do not edit manually)
package linaplugins

import (
    _ "lina-plugin-content-article/backend"
    // ... other plugins
)
```

## Database Access

Plugins use `GoFrame`'s `gf gen dao` command to generate the data access layer. A plugin's DAO layer is fully independent from the host's DAO layer, isolated through database namespaces and the tenant discriminator column. Tables that need multi-tenant support should include a `tenant_id` column, and queries should append tenant filtering conditions via the host's published tenant filtering capability; when the multi-tenant plugin is not enabled, `tenant_id = 0` represents the platform context.

```bash
# Run in the plugin backend/ directory
cd apps/lina-plugins/content-article/backend
gf gen dao
```

The `hack/config.yaml` configuration file points to the plugin's own tables:

```yaml
gfcli:
  gen:
    dao:
      - link: "pgsql:postgres:postgres@tcp(127.0.0.1:5432)/linapro?sslmode=disable"
        path: "internal"
        tables: "content_article_record"        # List plugin-owned tables explicitly; do not use wildcards
        importPrefix: "lina-plugin-content-article/backend/internal"
        descriptionTag: true
        noModelComment: true
```

## Frontend Pages

Plugin frontend pages go in the `frontend/pages/` directory. The framework auto-discovers and mounts them into the host workspace's dynamic routes:

```vue
<!-- frontend/pages/article-list.vue -->
<template>
  <div class="article-list">
    <!-- Use VXE Table to display the article list -->
    <vxe-grid v-bind="gridOptions" />
  </div>
</template>

<script setup lang="ts">
import { onMounted, ref } from 'vue'
// Import via relative path or use shared packages provided by the host
import { useRequest } from '@vben/hooks'

const { loading, data, run } = useRequest(() =>
  fetch('/api/v1/plugin/content-article/article')
)

onMounted(() => run())
</script>
```

## Lifecycle Hooks

Plugins can listen for host-published lifecycle events and execute their own logic at the appropriate time:

```go
// Listen for user login success event, record a login log
plugin.Hooks().RegisterHook(
    pluginhost.ExtensionPointAuthLoginSucceeded,
    pluginhost.CallbackExecutionModeAsync,  // Runs asynchronously, does not block login
    func(ctx context.Context, payload pluginhost.HookPayload) error {
        // Extract login information from the payload
        userName := pluginhost.HookPayloadStringValue(payload.Values(), pluginhost.HookPayloadKeyUserName)
        ip := pluginhost.HookPayloadStringValue(payload.Values(), pluginhost.HookPayloadKeyIP)
        return recordLoginLog(ctx, userName, ip)
    },
)
```

## Plugin Version Upgrade

When a plugin publishes a new version (update the `version` field in `plugin.yaml`), the upgrade workflow is:

1. Add idempotent incremental `SQL` files under `manifest/sql/` (new columns, new tables, etc. — all statements must use `IF NOT EXISTS`)
2. Update the `version` field in `plugin.yaml` to the new version number
3. Recompile the host; at startup, the host detects a mismatch between the installed version in the database and the declared version in the binary
4. When versions do not match, the host **refuses to start** and logs all pending plugins with their version differences
5. Execute the upgrade (run incremental SQL and update the registry) to align the database version with the binary version
6. Restart the host — the new version takes effect

Upgrade SQL follows the same design principles as installation SQL — all statements must be idempotent, and re-executing existing content must not produce errors. The host re-runs all files in the installation SQL directory during upgrade; only newly added statements actually produce changes.

## Best Practices

- Plugin `ID` uses `kebab-case`; the table prefix uses the corresponding `snake_case` (e.g., `content-article` → `content_article_`)
- Installation `SQL` uses `IF NOT EXISTS` to ensure idempotency
- All plugin service logic goes under `backend/internal/service/`; do not create `service/` elsewhere
- Menu `key` must use the `plugin:<plugin-id>:<menu-key>` format
- Uninstallation `SQL` covers complete cleanup logic, and `RegisterUninstallHandler` handles non-database resources like files
- Use `apps/lina-plugins/plugin-demo-source` as a development template
