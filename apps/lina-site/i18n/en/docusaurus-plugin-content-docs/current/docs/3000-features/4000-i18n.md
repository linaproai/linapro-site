## Overview

`LinaPro` ships with a complete internationalization runtime that supports per-request dynamic language switching, unified management of host and plugin language resources, and automatic merging of plugin language packs when they are enabled.

## Built-in Language Packs

The framework ships with two complete language packs — **English (`en-US`) and Simplified Chinese (`zh-CN`)** — covering all host UI copy, menu labels, error messages, and API documentation translations. Other languages (e.g., Traditional Chinese, Japanese) require users to create and maintain their own translation files; the framework does not provide default translations for those languages.

## Configuration

Configure internationalization behavior in `config.yaml`:

```yaml
i18n:
  # Default language (used when a request carries no language identifier)
  default: zh-CN
  # Enable multi-language; when off, the frontend hides the language switcher
  enabled: true
  # Language list (controls the order and display names in the frontend switcher)
  # Comment out a language to disable it
  locales:
    - locale: en-US
      nativeName: English
    - locale: zh-CN
      nativeName: 简体中文
```

## Directory Structure

Host language resources live under the `manifest/i18n/` directory:

```text
apps/lina-core/manifest/i18n/
├── zh-CN/
│   ├── framework.json         # Framework base copy
│   ├── menu.json              # Menu labels
│   ├── dict.json              # Dictionary type and data labels
│   ├── config.json            # System parameter copy
│   ├── error.json             # Error messages
│   ├── job.json               # Scheduled task copy
│   ├── notify.json            # Notification copy
│   ├── role.json              # Role-related copy
│   ├── plugin.json            # Plugin-related copy
│   ├── artifact.json          # Build artifact copy
│   ├── public-frontend.json   # Frontend public copy
│   └── apidoc/
│       ├── common.json        # Shared API doc translations (pagination, timestamps, etc.)
│       └── core-api-*.json    # Per-module API doc translations
└── en-US/
    └── (same structure as zh-CN, English translations)
```

The source repository currently only includes `zh-CN` and `en-US` directories. To add a new language, the project team must create the full directory structure, translate host and plugin resources, and register the language in the `config.yaml` `i18n.locales` list.

## Language Pack Format

Language packs use `JSON` format, supporting nested structures (recommended) or flat dot-separated keys:

```json
{
  "menu": {
    "dashboard": {
      "title": "Dashboard"
    },
    "iam": {
      "title": "Access Control",
      "user": {
        "title": "User Management"
      }
    }
  },
  "framework": {
    "description": "An AI-native full-stack framework for sustainable delivery"
  }
}
```

**Equivalent flat-key format:**

```json
{
  "menu.dashboard.title": "Dashboard",
  "menu.iam.title": "Access Control"
}
```

The framework normalizes nested `JSON` into flat keys at load time. When both formats are mixed, flat keys take precedence.

## Plugin Internationalization

Each plugin maintains its own language packs under its `manifest/i18n/` directory. When a plugin is enabled, the host automatically merges the plugin's language resources:

```text
apps/lina-plugins/content-article/manifest/i18n/
├── zh-CN/
│   ├── content-article.json         # Plugin runtime language pack
│   └── apidoc/
│       └── plugin-api-article.json  # Plugin API doc translations
└── en-US/
    └── content-article.json
```

Plugin language pack files are named after the plugin `ID` (`kebab-case`) to avoid key collisions with the host and other plugins:

```json
{
  "plugin": {
    "content-article": {
      "article": {
        "title": "Article Management",
        "status": {
          "draft": "Draft",
          "published": "Published"
        }
      }
    }
  }
}
```

## Adding a New Language

Adding a new language takes just three steps — **no `Go` code, `SQL`, or frontend `TypeScript` changes required**:

**Step 1: Register the language in `config.yaml`**

```yaml
i18n:
  locales:
    - locale: ja-JP
      nativeName: 日本語
```

**Step 2: Create the language resource directory**

```bash
mkdir -p apps/lina-core/manifest/i18n/ja-JP/apidoc
```

**Step 3: Create translation files**

Create the corresponding `JSON` translation files under `manifest/i18n/ja-JP/`, using the Chinese or English version as a template and translating each entry.

Once the translation files are in place and the service is restarted, the Japanese option will appear automatically in the management workspace language switcher. Note that the framework does not auto-generate translations for Japanese, Traditional Chinese, or other languages — missing translations fall back to default copy or display untranslated keys, depending on the call site.

## Translation Cache Management

Runtime language packs are loaded into an in-memory cache on the first request. After modifying translation files, you must invalidate the cache for changes to take effect.

**Restart the service (development):**

```bash
make stop && make dev
```

**Runtime cache invalidation (production, no restart required):**

The framework provides a scoped invalidation `API` accessible from the management workspace system endpoints. Cache invalidation scope granularity:

| Scope | Description |
|-------|-------------|
| Specific language | Invalidate only the cache for a given `locale` |
| Specific plugin | Invalidate only the translation cache for a given plugin |
| Full host | Invalidate all language caches for the host |

:::tip
Avoid clearing all languages and all sectors without reason — this causes brief translation jitter. Invalidate at the smallest necessary scope to minimize user impact.
:::

## Frontend Language Switcher

The frontend management workspace provides a language switcher in the top-right corner. Clicking it switches the interface language immediately. The available options come from the `i18n.locales` configuration.

When `i18n.enabled: false`, the frontend hides the language switcher and all copy uses the language specified by `i18n.default`.

## API Documentation Translation

API documentation (`/api.json`) descriptions also support multi-language translation (defaults to English when no translation is available). Translation files go in the `apidoc/` subdirectory:

```json
// manifest/i18n/zh-CN/apidoc/core-api-article.json
{
  "plugins": {
    "content-article": {
      "article": {
        "list": {
          "summary": "Article list",
          "description": "Paginated article list with optional status filter",
          "params": {
            "page": "Page number",
            "pageSize": "Page size"
          }
        }
      }
    }
  }
}
```

The `en-US` API doc translation directory is typically left as an empty placeholder — English source code comments serve as the default copy.

## Language Code Conventions

`LinaPro` uses standard `IETF BCP 47` language codes. Only `en-US` and `zh-CN` ship with complete language packs by default; other languages can be extended following the conventions below:

| Language | Code |
|----------|------|
| Simplified Chinese | `zh-CN` |
| Traditional Chinese | `zh-TW` |
| English | `en-US` |
| Japanese | `ja-JP` |
| Korean | `ko-KR` |

Directory names, `config.yaml` `locale` fields, and frontend `locale` parameters all use these codes consistently.
