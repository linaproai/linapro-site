## Overview

LinaPro ships with a complete i18n runtime that supports per-request language switching. Host and plugin locale resources are managed in a unified registry — when a plugin is enabled, its locale files are automatically merged into the runtime.

## Configuration

Configure internationalization behavior in `config.yaml`:

```yaml
i18n:
  # Default language used when a request carries no language identifier
  default: zh-CN
  # Whether multi-language support is enabled; disabling hides the language switcher in the frontend
  enabled: true
  # Language list (controls the order and display names in the frontend switcher menu)
  # Comment out a locale entry to disable it
  locales:
    - locale: en-US
      nativeName: English
    - locale: zh-CN
      nativeName: 简体中文
    - locale: zh-TW
      nativeName: 繁體中文
```

## Directory Structure

Host locale resources live under the `manifest/i18n/` directory:

```text
apps/lina-core/manifest/i18n/
├── zh-CN/
│   ├── framework.json         # Core framework copy
│   ├── menu.json              # Menu labels
│   ├── dict.json              # Dictionary type and entry names
│   ├── config.json            # System parameter copy
│   ├── error.json             # Error messages
│   ├── job.json               # Scheduled task copy
│   ├── notify.json            # Notification copy
│   ├── role.json              # Role-related copy
│   ├── plugin.json            # Plugin-related copy
│   ├── artifact.json          # Build artifact copy
│   ├── public-frontend.json   # Frontend shared copy
│   └── apidoc/
│       ├── common.json        # Shared API doc translations (pagination, timestamps, etc.)
│       └── core-api-*.json    # Per-module API doc translations
├── en-US/
│   └── (same structure as zh-CN, English translations)
└── zh-TW/
    └── (same structure as zh-CN, Traditional Chinese translations)
```

## Locale File Format

Locale files use JSON format and support either nested structure (recommended) or flat dot-separated keys:

```json
{
  "menu": {
    "dashboard": {
      "title": "工作台"
    },
    "iam": {
      "title": "权限管理",
      "user": {
        "title": "用户管理"
      }
    }
  },
  "framework": {
    "description": "面向可持续交付的 AI 原生全栈框架"
  }
}
```

**Flat key equivalent:**

```json
{
  "menu.dashboard.title": "工作台",
  "menu.iam.title": "权限管理"
}
```

At load time, the framework normalizes nested JSON into flat keys. When both formats are mixed, flat keys take precedence.

## Plugin Internationalization

Each plugin maintains its own locale files under `manifest/i18n/`. When a plugin is enabled, the host automatically merges the plugin's locale resources into the runtime:

```text
apps/lina-plugins/content-article/manifest/i18n/
├── zh-CN/
│   ├── content-article.json         # Plugin runtime locale
│   └── apidoc/
│       └── plugin-api-article.json  # Plugin API doc translations
└── en-US/
    └── content-article.json
```

Plugin locale files should be named after the plugin ID (in `kebab-case`) to avoid key collisions with the host and other plugins:

```json
{
  "plugin": {
    "content-article": {
      "article": {
        "title": "文章管理",
        "status": {
          "draft": "草稿",
          "published": "已发布"
        }
      }
    }
  }
}
```

## Adding a New Language

Adding a new language requires just three steps — **no Go code, SQL, or frontend TypeScript changes needed**:

**Step 1: Register the locale in `config.yaml`**

```yaml
i18n:
  locales:
    - locale: ja-JP
      nativeName: 日本語
```

**Step 2: Create the locale resource directory**

```bash
mkdir -p apps/lina-core/manifest/i18n/ja-JP/apidoc
```

**Step 3: Create translation files**

Under `manifest/i18n/ja-JP/`, create the corresponding JSON translation files. Copy the Chinese or English versions as a template and translate each entry.

After restarting the service, Japanese will automatically appear in the management workspace language switcher.

## Translation Cache Management

Runtime locale resources are loaded into an in-memory cache on first request. After modifying translation files, you need to invalidate the cache for the changes to take effect.

**Restart the service (development environment):**

```bash
make stop && make dev
```

**Runtime cache invalidation (production, no restart required):**

The framework provides a scoped cache invalidation API, accessible from the management workspace's system API panel. Available invalidation scopes:

| Scope | Description |
|-------|-------------|
| Specific locale | Invalidates only the cache for the specified locale |
| Specific plugin | Invalidates only the translation cache for the specified plugin |
| Full host | Invalidates all locale caches across the host |

:::tip
Avoid clearing all locales and all sectors without a specific reason — it causes brief translation flickering for users. Invalidate only what's necessary, at the smallest required scope.
:::

## Frontend Language Switcher

The management workspace provides a language switcher in the top-right corner of the page. Clicking it immediately switches the UI language. The available options are sourced from the `i18n.locales` configuration.

When `i18n.enabled: false`, the switcher is hidden and all UI text uses the language specified by `i18n.default`.

## API Documentation Translation

API documentation (`/api.json`) description text also supports multi-language translation (English is used as the fallback when no translation is found). Translation files are placed in the `apidoc/` subdirectory:

```json
// manifest/i18n/zh-CN/apidoc/core-api-article.json
{
  "plugins": {
    "content-article": {
      "article": {
        "list": {
          "summary": "文章列表",
          "description": "分页查询文章列表，支持按状态筛选",
          "params": {
            "page": "页码",
            "pageSize": "每页数量"
          }
        }
      }
    }
  }
}
```

The `en-US` API doc translation directory is typically left as an empty placeholder, with the English source-code comments serving as the default copy.

## Language Code Conventions

LinaPro uses standard IETF BCP 47 language codes:

| Language | Code |
|----------|------|
| Simplified Chinese | `zh-CN` |
| Traditional Chinese | `zh-TW` |
| English | `en-US` |
| Japanese | `ja-JP` |
| Korean | `ko-KR` |

Directory names in locale files, the `locale` field in `config.yaml`, and the `locale` parameter in the frontend all use this same set of codes consistently.
