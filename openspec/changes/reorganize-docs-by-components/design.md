## Context

当前 `apps/lina-site/docs/docs/` 的中文主稿已经覆盖 LinaPro 的架构、功能和扩展开发内容，但组织方式仍以“文档视角”为主：

- `2000-architecture/` 介绍整体架构、核心宿主、工作台、插件系统和分布式架构。
- `3000-features/` 介绍配置、接口文档、多租户、定时任务、插件管理和 `I18N`。
- `4000-plugin-development/` 介绍源码插件、`WASM`动态插件和扩展开发选型。

这些内容存在天然交叉。例如 `lina-core` 的设计同时散落在核心宿主、配置、接口文档、定时任务、`I18N` 和多租户页面中；插件系统的设计、管理和开发也分别位于三个目录。用户想理解一个组件时，必须跨目录追踪同一主题。

本次变更将中文主稿重组为“组件设计”目录，以 `apps/lina-site/docs/docs/2000-components/` 作为统一入口。用户明确要求：

- 不创建 `3000-lina-vben/`、`5000-distributed/` 或 `2000-lina-core/` 子目录。
- `2000-components/` 目录下需要有 `2000-components.md` 作为组件概览文档。
- 文件名前的数字用于排序，并按千位递增。
- 文档内容需要做整合，中文表达必须地道、通顺、易于理解。
- 不修改任何 `i18n` 目录内容，后续人工单独同步。

## Goals / Non-Goals

**Goals:**

- 建立 `2000-components/` 下以组件为中心的中文文档结构。
- 将旧“架构设计、功能特性、扩展开发”下的相关内容整合到组件页面中。
- 让每个组件页面同时覆盖设计理念、实现细节、功能特性、扩展开发接缝和使用方式。
- 使用千位递增的文件名前缀保持 Docusaurus 自动侧边栏顺序稳定。
- 保留现有 `slug`，降低旧链接、搜索索引和站内引用失效风险。
- 明确本次不触碰 `apps/lina-site/i18n/`，避免英文内容被半自动同步成不自然翻译。

**Non-Goals:**

- 不实现 LinaPro 主仓库功能变更。
- 不同步英文或其他语言文档。
- 不引入新的 Docusaurus 插件、搜索方案或路由重定向插件。
- 不重写快速体验、设计理念、社区或开发工具目录中与本次组件重组无关的内容。
- 不把所有旧文档原样搬迁到新目录；重复、过时或视角不匹配的内容需要整合、删减或改写。

## Decisions

### 决策一：`2000-components/` 下采用扁平文件结构

**Decision**

`2000-components/` 下不为 `lina-core`、`lina-vben`、分布式架构创建子目录。推荐目标结构如下：

```text
apps/lina-site/docs/docs/2000-components/
├── 2000-components.md
├── 3000-core-host.md
├── 4000-admin-workspace.md
├── 5000-plugin-system.md
├── 6000-source-plugins.md
├── 7000-wasm-plugins.md
├── 8000-plugin-management.md
└── 9000-distributed-architecture.md
```

**Rationale**

用户已经明确排除了 `3000-lina-vben/`、`5000-distributed/` 和 `2000-lina-core/` 目录。扁平结构可以让“组件设计”侧边栏更短、更直接，避免用户进入组件目录后再次面对多层分类。

**Alternatives considered**

- 按组件建子目录：适合文档规模很大时使用，但当前用户明确不希望这样组织。
- 保留旧三大目录：可以减少迁移工作，但无法解决同一组件内容分散的问题。

### 决策二：用 `2000-components.md` 作为组件概览页

**Decision**

`2000-components.md` 不是简单索引页，而是“组件设计”的组件概览文档。它应直接说明：

- `LinaPro` 的核心框架组件。
- 每个组件的运行形态和核心职责。
- 各组件在宿主、工作台、插件和分布式运行时之间的协作关系。
- `API`契约、插件治理和运行时协调三条主要协作主线。

**Rationale**

Docusaurus 的自动侧边栏会直接展示页面列表。组件概览页用于先说明框架组件本身，避免入口页变成信息架构说明或阅读路径说明。

**Alternatives considered**

- 仅依赖 `DocCardList`：可以展示列表，但无法说明框架组件职责和协作关系。
- 只使用 `_category_.json`：可以控制目录标签，但不能承载正文说明。

### 决策三：按千位递增编号排序

**Decision**

所有 `2000-components/` 下的 Markdown 文件使用千位递增前缀，例如 `2000`、`3000`、`4000`。不得使用 `2100`、`2200` 或类似百位细分编号。

**Rationale**

千位编号为后续插入新组件预留空间，同时保持当前目录排序规则简单一致。用户已经明确数字用于排序且按千位递增。

**Alternatives considered**

- 使用百位细分编号：可表达更细层级，但不符合本次用户约束。
- 取消数字前缀，依赖 front matter 排序：可读性更强，但当前仓库已有数字排序习惯，直接变更会扩大影响。

### 决策四：内容整合以组件为主线，而不是机械搬迁

**Decision**

每个新页面按组件主线重写和整合旧内容：

| 新文档 | 主要整合来源 | 重点 |
|---|---|---|
| `2000-components.md` | 原架构总览、功能特性总览、扩展开发总览 | 框架组件概览、组件职责和协作关系 |
| `3000-core-host.md` | 核心宿主服务、配置管理、接口文档、定时任务、`I18N`、多租户宿主侧内容 | `lina-core` 的设计、能力、配置和扩展接缝 |
| `4000-admin-workspace.md` | 默认管理工作台 | `lina-vben` 如何消费宿主和插件能力 |
| `5000-plugin-system.md` | 双模式插件系统、扩展开发总览、插件生命周期和隔离机制 | 插件系统的治理主链和边界规范 |
| `6000-source-plugins.md` | 源码插件 | 源码插件的设计理念、目录结构、注册机制和开发流程 |
| `7000-wasm-plugins.md` | `WASM`动态插件 | 动态插件的沙箱、桥接协议、构建、安装和运行方式 |
| `8000-plugin-management.md` | 插件管理、插件系统管理端内容 | 插件来源、安装、升级、启用、禁用和卸载 |
| `9000-distributed-architecture.md` | 原生分布式架构、配置中的 Redis 协调、定时任务集群内容 | 单机/集群模式、选主、锁、缓存和任务防重复 |

**Rationale**

这次重组的价值在于减少认知跳转，而不是改变文件路径。若只是搬迁旧页面，重复内容和跨目录引用仍然存在。

**Alternatives considered**

- 原文搬迁后再逐步优化：迁移速度快，但会保留旧结构的问题。
- 完全重写所有页面：质量上限更高，但容易脱离 LinaPro 主仓库事实，风险更大。更稳妥的方式是以现有文档和主仓库事实为基础重写整合。

### 决策五：保留已有 `slug`

**Decision**

迁移后的页面尽量保留原有 `slug`，例如：

- `3000-core-host.md` 继续使用 `/docs/core-host`。
- `5000-plugin-system.md` 继续使用 `/docs/plugin-system`。
- `9000-distributed-architecture.md` 继续使用 `/docs/distributed-architecture`。

新建的目录介绍页使用新的稳定 `slug`，例如 `/docs/components`。

**Rationale**

当前大量文档已经用显式 `slug` 暴露稳定路径。目录重组不必等同于 URL 重组，保留 `slug` 可以避免站内链接、外部链接和搜索索引大面积失效。站点当前没有配置重定向插件，直接改 URL 会扩大验证范围。

**Alternatives considered**

- 改为 `/docs/components/...` 新 URL：语义更统一，但需要额外重定向治理，不适合本次范围。
- 删除 `slug` 使用文件路径 URL：会让 URL 随目录结构变化，不利于长期稳定。

### 决策六：显式排除 `i18n`

**Decision**

本次只修改中文主稿和必要的中文侧边栏相关结构，不修改 `apps/lina-site/i18n/` 下任何文件。

**Rationale**

用户明确要求 `i18n` 内容单独手动同步。组件重组后的英文文档需要地道英文表达，不能由中文重组结果机械翻译；将其排除可以避免半成品英文进入默认语言内容。

**Alternatives considered**

- 同步重排英文目录：结构更一致，但违反用户要求。
- 删除英文旧内容：会破坏当前英文站点，不可接受。

## Risks / Trade-offs

- [中文侧边栏和英文侧边栏短期不一致] → 本次明确只处理中文主稿，最终说明中记录 `i18n` 未同步，后续由人工同步。
- [旧页面删除或移动导致站内链接断裂] → 保留 `slug`，并在实现后运行构建或链接检查。
- [内容整合后页面过长] → 每个页面按“设计理念 / 架构与边界 / 核心能力 / 扩展与使用 / 相关文档”组织，必要时删减重复内容而不是继续堆叠。
- [组件边界不清导致重复说明] → 以 LinaPro 主仓库源码结构为事实依据，将跨组件能力放在最主要的归属页面，其他页面只保留必要引用。
- [Docusaurus 自动侧边栏顺序异常] → 文件名统一使用千位前缀，并为目录页设置明确 `title` 和 `slug`。

## Migration Plan

1. 盘点旧目录下所有待整合文档的 front matter、`slug`、标题、站内链接和主要章节。
2. 在 `2000-components/` 下创建目标文档结构，先落 `2000-components.md` 目录介绍页。
3. 逐篇整合旧文档内容，按组件主线重写中文表达，删除重复和过时描述。
4. 更新中文主稿中的站内链接，使链接仍指向保留的稳定 `slug`。
5. 移除或清空旧的 `2000-architecture/`、`3000-features/`、`4000-plugin-development/` 中文入口，确保中文侧边栏不再呈现旧分类。
6. 运行格式检查、站点构建或至少 Docusaurus 文档链接检查，确认没有明显断链和构建错误。

回滚方式为恢复旧目录和旧文档文件；由于保留 `slug`，回滚不涉及额外数据迁移。

## Open Questions

- 插件系统相关页面是否最终也完全打平到 `2000-components/`，还是保留一个插件系统子目录？当前推荐完全打平，除非实现时发现页面数量继续扩张。
- `3000-core-host.md` 是否需要吸收全部配置、接口文档、定时任务、`I18N` 和多租户内容，还是为部分能力保留独立页面？当前用户要求千位递增且目录打平，推荐先整合到核心宿主页面，避免 `2000-components/` 下页面过多。
