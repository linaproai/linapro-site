## Context

当前 `linapro-site` 仓库几乎为空，尚未具备任何官网代码、内容目录或发布基线；但 LinaPro 主仓库已经形成了相对稳定的产品定位、模块边界、插件生态和 OpenSpec 研发方式。官网一期的核心问题不是“先把页面搭出来”，而是先确定站点承载模型、内容来源边界和多语言策略，避免后续实现时出现以下偏移：

- 官网被误做成只展示后台工作台的营销页，而没有承载框架定位、插件体系和 OpenSpec 工作流。
- 文档、博客和 About 被拆散到不同实现中，导致导航、语言和 SEO 策略不一致。
- 团队资料、安装要求、搜索与 SEO 能力在没有统一规则时被随意填充，造成公开信息失真。

本次设计面向官网一期上线基线，服务对象包括：

- 首次认识 LinaPro 的外部访问者
- 希望快速安装与评估 LinaPro 的开发者
- 需要查阅框架、插件与 OpenSpec 文档的贡献者
- 后续负责继续补充官网内容与实现功能的维护者

## Goals / Non-Goals

**Goals:**
- 用一个统一站点承载首页、文档、博客和 About 页面。
- 明确官网一期的信息架构、内容边界、语言策略和 SEO 基线。
- 让实现阶段能够直接按页面和模块落地，而不再重新讨论站点组织方式。
- 为后续接入真实登录系统、团队资料和更多博客内容保留可扩展空间。

**Non-Goals:**
- 本次不实现真实用户登录、注册、会话或账号体系。
- 本次不建立自动从 LinaPro 主仓库实时抓取内容的同步系统。
- 本次不引入商业化插件市场、评论系统或复杂 CMS。
- 本次不强行解决 LinaPro 主仓库中尚未统一的所有安装版本口径，只为官网保留显式待确认边界。

## Decisions

### 决策一：一期采用单体 Docusaurus 站点，而不是“官网 + docs 双项目”

**Decision**

官网一期采用单个 Docusaurus 站点统一承载：

- 首页与品牌页面
- 文档站
- 博客
- About 页面
- 登录/注册占位页

**Rationale**

- Docusaurus 天然支持 docs、blog、pages、i18n 和静态 SEO 输出，足够覆盖一期范围。
- 单站模型可以保持统一导航、主题、语言切换、搜索入口和部署方式。
- 当前仓库为空，从零起步时先拆成多个站点只会增加信息架构和部署复杂度。

**Alternatives considered**

- “营销官网 + 独立文档站”双项目：更适合内容规模很大或团队分工明确的成熟站点，但对当前一期范围来说过重。
- 自定义 Next.js / React 站点：自由度更高，但会重新发明文档、博客、i18n 和静态内容能力，收益不足。

### 决策二：官网内容以本仓库手工编排为准，主仓库作为事实来源而非运行时依赖

**Decision**

官网内容由 `linapro-site` 仓库内的文档与页面文件承载，内容编写时以 LinaPro 主仓库的 README、插件说明和 OpenSpec 规范为事实来源，但不在构建时直接远程抓取或动态依赖主仓库。

**Rationale**

- 官网需要对外呈现经过整理的叙事，而不是把源仓库内容原样搬运。
- 手工编排更容易控制首页叙事、文档结构、SEO 标题和双语镜像。
- 避免主仓库结构变化或网络不可用导致官网构建不稳定。

**Alternatives considered**

- 构建时同步主仓库 Markdown：自动化更强，但会引入跨仓库耦合、格式漂移和构建脆弱性。
- Git submodule / subtree 镜像：可复用内容，但对当前一期来说维护成本仍偏高。

### 决策三：默认语言使用英文，简体中文作为镜像语言

**Decision**

站点默认语言设为英文，简体中文作为同步镜像语言；核心页面和关键文档必须提供双语版本。

**Rationale**

- LinaPro 主仓库当前采用 `README.md` 为英文主文档、`README.zh_CN.md` 为中文镜像的治理方式。
- 官网面向开源项目对外发布，默认英文更利于统一对外入口。
- 中文镜像仍是刚需，必须在首页、文档首页、博客入口和 About 页面保持可达。

**Alternatives considered**

- 默认中文：更贴近当前对话语言，但会削弱与主仓库英文主文档的对齐关系。
- 中英分站：结构更清晰，但会增加维护负担和 SEO 重复内容治理成本。

### 决策四：搜索一期先满足站内搜索能力，不绑定必须依赖外部 SaaS

**Decision**

官网一期的目标是先具备覆盖文档与博客的站内搜索能力，优先选择能在静态站点中稳定工作的搜索集成路径；是否升级为外部托管搜索服务留作后续演进。

**Rationale**

- 用户当前明确需要“可搜索”，而不是必须一步到位接入外部搜索平台。
- 一期应优先保证搜索可用、部署简单、内容更新链路稳定。
- 后续若内容规模增长，再演进到 Algolia DocSearch 等托管方案更合适。

**Alternatives considered**

- 直接绑定外部托管搜索：效果更强，但需要额外申请、审核或索引配置，不利于一期快速成站。
- 完全不做搜索：不满足明确需求。

### 决策五：About、Login、Register 采用真实边界占位策略

**Decision**

About 页面保留团队、联系方式和社区入口结构，但在真实资料缺失前只使用明确占位。`/login` 与 `/register` 提供真实风格的预留页，但仅说明后续对接 LinaPro 用户系统，不提供伪交互流程。

**Rationale**

- 官网一期必须把未来入口占住，否则后续导航结构会变化。
- 对外页面不能伪造成员资料、邮箱或认证能力，这会直接损伤可信度。
- 用真实边界占位可以同时满足产品预留与公开透明。

**Alternatives considered**

- 直接隐藏 About / Login / Register：实现更简单，但不满足当前需求，也不利于导航稳定。
- 伪造团队资料或表单流程：风险过高，禁止采用。

### 决策六：安装与运行要求在官网中显式区分“已确认”和“待统一”

**Decision**

官网实现时对安装与运行要求采用“显式确认后发布”的方式：只有与主仓库实现和规范一致的信息才进入最终安装说明；发现版本冲突时，在内容整理阶段先标记为待统一而不是擅自选择其一。

**Rationale**

- 当前主仓库存在 Go、Node、pnpm、数据库口径不一致的问题。
- 官网一旦公开写死版本要求，就会成为对外承诺，错误成本高于实现内部文档。

**Alternatives considered**

- 直接照搬 README：最快，但会把冲突正式对外放大。
- 完全不写安装信息：不能满足官网一期文档目标。

## Risks / Trade-offs

- [主仓库内容与官网文案继续漂移] → 通过“主仓库为事实来源、官网手工整理发布”的规则降低漂移，并在后续评审中核对来源文件。
- [多语言内容不同步] → 将首页、文档首页、博客入口和 About 设为必做双语镜像，先缩小必须同步的范围。
- [一期搜索方案能力有限] → 先确保搜索可用，后续再根据内容规模升级搜索基础设施。
- [About 页面显得信息不足] → 明确保留结构和占位说明，避免用虚假内容“填满”页面。
- [安装说明迟迟无法发布] → 在实现阶段把版本冲突列为阻塞项，只有统一后再写入最终文档。

## Migration Plan

1. 在当前仓库建立 Docusaurus 站点基础结构与 OpenSpec 规范基线。
2. 按首页、文档、博客、About、登录/注册占位页的顺序落站点页面。
3. 将 LinaPro 主仓库中的可公开内容整理为本仓库内的文档与页面内容。
4. 接入双语能力、站点搜索和基础 SEO 配置。
5. 在预览环境验证导航、语言、搜索、元数据和静态输出后再公开部署。

本次变更没有历史站点数据需要迁移；回滚方式为回退到前一个静态站点构建版本。
