## Context

官网现有插件系统文档位于`apps/lina-site/docs/docs/2000-components/5000-plugin-system/`，包含5篇文档：

- `5000-plugin-system.md`：治理主链、生命周期、隔离机制
- `6000-source-plugins.md`：源码插件开发指南
- `7000-wasm-plugins.md`：WASM动态插件
- `8000-plugin-management.md`：插件管理
- `9000-plugin-config-and-manifest.md`：插件配置与manifest资源

源码中`capability.Services`接口持续演进，当前包含`AI()`、`APIDoc()`、`Auth()`、`Users()`、`BizCtx()`、`Cache()`、`Dict()`、`Files()`、`HostConfig()`、`I18n()`、`Infra()`、`Jobs()`、`Manifest()`、`Notifications()`、`Org()`、`Plugins()`、`Route()`、`Sessions()`和`Tenant()`等插件可见领域能力。`pluginhost.Services`在此基础上扩展`Admin()`和`TenantFilter()`，动态插件还通过`pluginbridge`发布`Runtime()`、`Network()`、`RecordStore()`等动态专属能力，并通过`hostServices`声明`runtime`、`infra`、`storage`、`network`、`data`、`lock`、`jobs`等服务。现有文档在`6000-source-plugins.md`中简要提及了`Services()`和部分服务，但缺少系统性的架构说明。

源码参考路径：
- 接口定义：`apps/lina-core/pkg/plugin/capability/capability.go`
- 领域合约：`apps/lina-core/pkg/plugin/capability/*cap/*.go`
- 组织能力：`apps/lina-core/pkg/plugin/capability/orgcap/orgcap.go`
- 租户能力：`apps/lina-core/pkg/plugin/capability/tenantcap/tenantcap.go`
- 插件宿主：`apps/lina-core/pkg/plugin/pluginhost/pluginhost.go`
- 动态服务描述符：`apps/lina-core/pkg/plugin/pluginbridge/internal/hostservice/hostservice_descriptor.go`

侧边栏使用`autogenerated`配置，新增目录会自动纳入导航。

## Goals / Non-Goals

**Goals:**

- 为插件开发者提供`Services`架构的系统性认知，理解各服务的定位、边界和协作关系
- 每篇文档聚焦设计思路、架构位置和设计约束，帮助开发者建立正确的使用心智模型
- 与现有插件系统文档形成互补：现有文档讲"怎么做"，新文档讲"为什么这样设计"
- 文档结构与源码合约包保持对应关系，便于后续维护

**Non-Goals:**

- 不创建API参考文档，不逐方法展开参数细节和完整使用示例
- 中文主稿确认后同步英文`i18n`镜像
- 必要时修改现有插件能力文档，保证目录按领域能力维度组织
- 不覆盖`pluginhost`的注册机制（`Assets`/`HTTP`/`Hooks`/`Cron`/`Lifecycle`/`Governance`），这些已在`6000-source-plugins.md`中介绍

## Decisions

### 1. 目录位置：嵌套在`5000-plugin-system/`内部

**选择**：`5000-plugin-system/9000-capabilities/`

**备选方案**：`2000-components/6000-plugin-capabilities/`（与`5000-plugin-system/`平级）

**理由**：插件领域能力是插件系统的子主题，嵌套在插件系统目录下保持了内容层级的语义一致性。平级放置会稀释插件系统文档的聚合度。`sidebars.ts`使用`autogenerated`，嵌套目录会自动显示为子分类。

### 2. 按领域能力组织文档

**选择**：以父领域能力作为文档拆分单位。`Plugins().State()`、`Plugins().Lifecycle()`、`Plugins().Config()`等子能力放入`Plugins()`文档；`TenantFilter()`放入`Tenant()`文档；`AI`文本、图片、向量、音频、视觉、文档、安全和视频能力放入`AI`文档。

**理由**：插件开发者按业务领域选择能力，而不是按内部服务适配器选择能力。把子能力收进父领域文档，可以减少短页面和重复解释，并让治理边界在同一上下文中呈现。

### 3. 配置管理保留关系介绍页

**选择**：`7000-config.md`作为配置关系介绍页，说明`Plugins().Config()`、`HostConfig()`、`Admin().Config()`、动态`config.get`和`hostconfig.get`之间的定位差异；具体使用边界分别放入所属领域文档。

**理由**：配置能力跨越插件治理、宿主配置和运行时配置管理三个领域。如果全部合并成一篇方法说明，会掩盖领域边界；如果完全分散，又会让开发者难以判断应使用哪个入口。关系介绍页负责建立导航和对比。

### 4. Org和Tenant文档包含Provider实现指引

**选择**：在`7400-org.md`和`7900-tenant.md`中额外包含提供方`Provider`接口说明

**理由**：`orgcap`和`tenantcap`是框架级能力扩展点，插件开发者既可能是消费者也可能是提供方。在架构文档中说明`Provider`角色和注册机制，有助于理解整个能力供给链的设计。

### 5. 文档统一结构

**选择**：每篇服务文档遵循以下结构：

```
## 基本介绍
## 设计思路
## 架构位置（mermaid图）
## 主要能力（方法概览表格）
## 设计约束
## 相关服务
```

**理由**：统一结构降低阅读认知负担，也便于后续维护和自动化检查。mermaid图用于展示服务在请求链路或插件生命周期中的位置，表格用于方法概览而非详细API文档。

### 6. 中文先行，英文同步

**选择**：先维护`apps/lina-site/docs/docs/`中文主稿，再同步到`apps/lina-site/i18n/en/docusaurus-plugin-content-docs/current/`英文镜像。

**理由**：仓库以中文主稿作为官网文档事实源，但当前默认站点语言仍为`en`。能力文档确认后必须同步英文，避免英文根路径继续展示过期能力清单。

## Risks / Trade-offs

**[文档与源码同步风险]** → 源码接口变更时文档可能滞后。缓解措施：文档聚焦设计思路而非方法签名，设计层面的变更频率低于API层面；文档中引用源码路径，便于开发者自行对照。

**[文档数量较多]** → 维护成本增加。缓解措施：以领域能力合并子能力文档，避免`PluginState`、`PluginLifecycle`、`TenantFilter`这类子能力单独成页。

**[中英文内容漂移]** → 能力清单变化时英文镜像可能滞后。缓解措施：中文主稿变更后使用 dirty i18n 同步流程，仅同步本次变更文档，并在验证阶段检查链接、`slug`和关键能力名。
